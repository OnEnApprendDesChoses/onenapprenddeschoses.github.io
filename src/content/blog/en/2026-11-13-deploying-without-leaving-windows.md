My app was coded. It was even on GitHub. All that remained was the last step,
the one you think is a single command line: putting it online.
Except my PC runs Windows, the deployment tool politely refuses to exist
for Windows, and I had no intention of installing Ubuntu. This post is how
we got away with it, and everything I learned along the way.

## The problem: a CLI that doesn't exist on my machine

To deploy an app on the platform, the documentation says: run `mistral deploy`.
Except that command lives inside a command-line tool that only exists for
Linux and macOS. On Windows: "Unsupported operating system". The "official"
solution would have been to install WSL, a sort of Linux inside Windows.
I said no. Not on principle, but because my PC was working perfectly well,
and adding an entire system layer just to run one command felt
disproportionate.

## The find: deploy from GitHub, not from my PC

Then an idea: the deployment command doesn't need to run on *my* machine.
It just needs to run *somewhere*, with access to my code. My code is on
GitHub. GitHub provides virtual machines to run automated tasks
(GitHub Actions), and those machines run Linux.

So I wrote a small configuration file that tells GitHub: "every time I
push code, install the deployment tool and deploy". All of it
authenticated by an API key stored in the repository's secrets, never
in the code. Result: I installed nothing, and as a bonus, every future
`git push` updates my app automatically. I didn't know yet that this
little file would give me a whole evening of debugging.

## The CLI's lie detector

First mystery: the deploy command appears and disappears across runs.
Same command, same tool version, sometimes "Unknown subcommand \"deploy\"",
sometimes it works. Cross-referencing the logs revealed the truth: the tool
*hides* its deployment command until it manages to validate the API key at
startup. When the platform hiccups, validation fails, the command hides,
and the error message sends you chasing a problem that doesn't exist.
Moral: an error message is not a diagnosis. And the workaround is humble:
retry a few times, with a little patience between attempts. Four tries
spaced 90 seconds apart, and the hiccups resolve themselves.

## The invisible file

Second mystery: my API started, connected to its database, ran its
migrations... then crashed demanding a `uv.lock` file I had never heard
of. That's a "lock file": the exact list of versions of the Python
libraries in use. The build needs it to rebuild the environment
faithfully. The file was supposed to be generated by a tool I didn't
have, and it had been missing from the start. Generated, pushed,
re-deployed: that puzzle piece vanished.

## The security rule that protects better than it annoys

Third mystery, my favorite. The API crashed at startup with an explicit
error: `UndeclaredAccessRuleError`. The framework requires every piece
of API to declare *who is allowed to call it*: a list of authentication
dependencies, empty if the piece is public. My routes had declared
nothing, and by default the framework refuses to guess, because
"guessing" would mean "make public by silence". It's the kind of design
decision that feels annoying at 11 pm, and is exactly what you want in
code that ends up on the Internet. One empty list, two lines, one
commit, and my API finally started.

## Verdict

The app is live. The database runs, the API answers, the interface is
served. What I learned, in no particular order:

- **A deployment doesn't need your machine.** GitHub Actions (or an
  equivalent) moves the problem to machines that know how to do it.
- **Transient errors exist.** Retry before diagnosing.
- **Lock files are not decoration.** Without them, a reproducible
  build isn't.
- **Security by default should be annoying.** That's its job.

And all I wanted was not to install Ubuntu.
